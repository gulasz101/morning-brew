## 8. Go Was Silently Accepting This JSON #golang #typescript #programming, by Better Stack

**In short:** Better Stack's short shows Go's original JSON decoder silently takes the last duplicate key, while encoding/json/v2 rejects it outright. I would say that is the right default, and a small comfort if you parse anything security-sensitive.

**Key points:**
- Better Stack published the short on Go JSON parsing behaviour.
- The example object contains two role values, user then admin.
- The original encoding/json accepts it with no error and uses admin.
- encoding/json/v2 returns an error on the duplicate key instead.
- V2 rejects the JSON to remove ambiguity between parsers.

**Details:** Go's original JSON decoder is the quiet kind of dangerous here. Feed it an object with role set twice, first user and then admin, and it does not complain; it just uses admin. That is the bad news, and it is easy to miss in a code review.

The V2 decoder does the opposite. It rejects the duplicate key outright, so the JSON never reaches the permission check with two possible meanings. Different parsers disagree on first versus last, and that disagreement is exactly where auth bugs hide.

I would say V2 is the sane default, and the old behaviour is the kind of thing that makes me nervous about accepting JSON near anything that matters. Nothing for my projects.
